## Что реализовано

| Направление | Изменение |
|---|---|
| Изоляция и безопасность | Claim ACL распространён на прямые операции, экспорт, sync, `undo_last`, transaction, review queue, preference rules, entity graph, локальные secret metadata, сессии и audit. Новые строки имеют owner/scope; старые строки с неизвестным владельцем закрыты по умолчанию. Для старого графа и вспомогательных таблиц есть отдельная операторская миграция с явной картой владельцев и резервной копией. |
| Восстановление | Модель может создать подписанный снимок только своих подходящих claims, перечислить его и слить назад. При восстановлении проверяются владелец, подпись, ссылки и конфликты ID. Полный архив и замена всей БД остаются операциями доверенного хоста. Секретные, карантинные и непубличные claims в scoped снимок не попадают. |
| Граф и происхождение | Сущности и связи получили owner/scope, ссылки на исходный claim, интервал действия и поиск по двум переходам. Есть явное, выключенное по умолчанию извлечение отношений через OpenRouter из одного видимого claim с проверкой результата перед записью. |
| Общая память между агентами | Блоки выбранных claims создаются владельцем; получатель должен получить grant и отдельно attach. Текст проверяется снова при чтении, а revoke и смена исходного claim прекращают выдачу. Подключённые блоки входят в `pack_context` и ограниченный автоматический `prefetch`. |
| Источники | Локальные файлы и текстовые записи с URI/revision подключены к документному графу и необязательной семантической индексации. Есть инкрементальные обновления, удаление и ограничение источников по scope. Прямые коннекторы GitHub Contents и Google Drive используют фиксированные API-хосты, ограниченные файлы, ревизии/условные запросы и отдельную авторизацию. Модельный ввод помечается непроверенной записью, а не выдаётся за подтверждённый удалённый источник. |
| Переносимость | Python SDK и MCP stdio wrapper задают устойчивые явные идентификаторы чата, бота и проекта. Отдельные процессы с разными владельцами не получают claims друг друга в тесте. |
| Поиск и диагностика | Исправлены лишние записи миграции при старте, `DELETE` в FTS, маршруты диагностики с нежелательными изменениями, выдача без учёта scope и сообщение `immediately_recallable` для claim, который поиск отфильтровывает. Добавлены воспроизводимые тестовые корпуса и измерители. |
| Пакетные изменения | `memory_wiki_transaction` атомарно применяет 2–50 операций `update_claim`, `rewrite_claim`, `merge_claims` с одной SQLite-транзакцией для claims, evidence, FTS-триггеров, outbox и журнала мутаций. Ошибка любого шага откатывает весь пакет; остальные виды многооперационных пакетов отвергаются до записи. Одиночный режим и предварительный `suggest` сохранены. |
| Эпизодическая память | При явном `MEMORY_WIKI_EPISODIC_ENABLED=1` доверенный `sync_turn` сохраняет короткие очищенные реплики пользователя и ассистента отдельно от claims. Новый `memory_wiki_query_episodes` ищет их в отдельном FTS с SQL-ограничением по bot/chat, TTL, квотой и повторной защитой вывода. Автоматический prefetch эпизодов реализован с отдельным `MEMORY_WIKI_EPISODIC_PREFETCH=1`, host-attested session ID и ограничением объёма; оба флага по умолчанию выключены. |

Детали и параметры приведены в [README](README.md); ключевые файлы — [`__init__.py`](__init__.py), [`schema.sql`](schema.sql), [`shared_blocks.py`](shared_blocks.py), [`source_connectors.py`](source_connectors.py), [`episodic_memory.py`](episodic_memory.py), [`sdk.py`](sdk.py) и [`tools/migrate_legacy_graph.py`](tools/migrate_legacy_graph.py). Схемы нативного провайдера, plugin manifest и MCP wrapper сведены к **119 инструментам**.

### Отличия после внедрения

| Сравнение | Текущее положение Memory Wiki |
|---|---|
| [Mem0 Graph Memory](https://docs.mem0.ai/open-source/features/graph-memory) | Теперь есть привязанный к claim граф и явное извлечение отношений через OpenRouter. Автоматическое извлечение из каждого диалога намеренно не включено: оно повысило бы сетевые расходы и риск записать ошибочную связь без подтверждённого источника. |
| [Graphiti](https://help.getzep.com/v2/graphiti/getting-started/overview) | Добавлены происхождение и время действия связей, два перехода графового поиска. Memory Wiki остаётся claim-first плагином Hermes, а не общей эпизодической графовой библиотекой; длинные диалоги в наших внешних замерах всё ещё вызывают пропуски. |
| [Letta memory blocks](https://docs.letta.com/tutorials/attaching-detaching-blocks/) | Есть явные grant/attach/detach/revoke для общих блоков с повторной проверкой исходных claims; блоки включаются в обычный bounded prefetch. |
| [OpenMemory](https://github.com/CaviraOSS/OpenMemory) | Есть Python SDK, MCP wrapper и источники local/GitHub/Drive. Преимущество Memory Wiki — нативные Hermes hooks, SQLite-журнал и восстановление; сложность — большая поверхность из 119 инструментов и привязка к жизненному циклу Hermes. |

Ни одна строка не утверждает превосходство по точности: опубликованные результаты этих проектов не запускались здесь на одном протоколе и бюджете.

## Замеры на синтетических данных

`benchmarks/quality_eval.py` создаёт временный `HERMES_HOME` и 14 искусственных claims для девяти вопросов: коррекция во времени, два шага, противоречие, видимость по chat/bot/project. Он напрямую заполняет SQLite, поэтому измеряет извлечение, а не качество автоматической записи или жизненный цикл диалога. Запуск без сети: Recall@5 = **1,0** на девяти случаях; запрещённых находок и нарушений scope — **0**. Запуск с действующими OpenRouter embeddings и Qdrant: Recall@5 = **1,0**, нарушений scope — **0**, p50 гибридного поиска **1242,87 мс**, p95 **4947,48 мс**. Создана отдельная случайная коллекция; проверка Qdrant после работы не обнаружила оставшихся коллекций с префиксом оценщика. Время холодного сетевого запроса переменно, а корпус мал — эти числа не являются оценкой реальной нагрузки.

Повторный `benchmarks/audit_retrieval.py` на 1500 синтетических claims в трёх изолированных прогонах дал медианы: перестройка FTS **176,96 мс**, первый старт **1879,82 мс**, устойчивый старт **341,95 мс**, p50 точного FTS-поиска **2,89 мс**, p95 **3,08 мс**; Recall@5 = **1,0**. Исторический первый старт после предыдущего патча был 1718–1759 мс, устойчивый 334–340 мс. Нынешний первый старт медленнее примерно на 8 % в этой небольшой серии, но условия Windows, кеш и разросшийся код менялись; причинно приписать разницу одному изменению нельзя. Самая первая одиночная baseline-точка была 1895,69 мс. Никаких данных из рабочей памяти этот замер не читал.

`benchmarks/answer_eval.py` передал найденные искусственные факты модели `openai/gpt-4.1-mini` через OpenRouter. При первом строгом оценивании **8/9** ответов удовлетворили прозрачным правилам: на конфликте модель сообщила неопределённость, но не указала, почему текущая политика лучше непроверенной заметки (p50 ответа **1158,90 мс**, p95 **1842,21 мс**). Явная инструкция различать текущий и непроверенный факт дала **9/9**, но в одном ответе модель без основания назвала текущий факт «проверенным». Оценщик дополнен запретом такого вывода и инструкция уточнена; заключительный повтор дал **9/9**, p50 **1213,58 мс**, p95 **1464,00 мс**, 1341 входной и 167 выходных токенов. Это проверка простой схемы RAG с отдельным prompt, а не полного Hermes prompt/prefetch; она не подтверждает качество на реальных беседах.

Для [LongMemEval](https://github.com/xiaowu0162/LongMemEval) добавлен отдельный адаптер. Полный прогон [официального очищенного oracle JSON, commit `98d7416`](https://huggingface.co/datasets/xiaowu0162/longmemeval-cleaned/blob/98d7416/longmemeval_oracle.json) занял **601,74 с** на 500 вопросах: 470 вопросов с размеченными источниками и 30 abstention. На FTS-only top‑5 session recall-all = **0,7915**, recall-any = **0,9638**, MRR = **0,9638**, turn recall-all = **0,4766**, p50 самого поиска **17,8 мс**. Политика записи приняла 6873 хода, поставила в очередь 4076, пропустила 11 из-за недоступного опционального `hermes_secret_core` в изолированной среде; ни один из 11 не был размеченным ответным ходом. Из 896 размеченных ответных ходов 794 были индексированы, 102 поставлены в очередь. Для multi-session вопросов session recall-all = **0,5785** (121 оцениваемый вопрос), так что ограничение FTS/записи существенно и не скрыто общей цифрой. Это oracle retrieval с изолированными профилями: он не генерирует ответы, не использует Qdrant/OpenRouter и не равен официальной end-to-end оценке QA. Для сравнения с [Mem0 Graph Memory](https://docs.mem0.ai/open-source/features/graph-memory), [Graphiti](https://help.getzep.com/v2/graphiti/getting-started/overview), [Letta shared blocks](https://docs.letta.com/tutorials/attaching-detaching-blocks/) и [OpenMemory](https://github.com/CaviraOSS/OpenMemory) см. исходный аудит. Реализованные owner graph, provenance, attach/detach и SDK сокращают перечисленные там функциональные различия.

На пяти заранее выбранных официальных LongMemEval oracle-вопросах (по одному из knowledge-update, multi-session, assistant, user и temporal) использованы действующие OpenRouter embeddings и Qdrant. И гибридный поиск, и FTS-only дали session recall-all@5 **0,8**, turn recall-all@5 **0,6**; p50 поиска составил **1713,86 мс** против **8,41 мс** у FTS. Один из пяти assistant-примеров полностью попал в очередь качества, поэтому семантический индекс не мог вернуть пропущенные claims. Это слишком малая и специально выбранная выборка для общего вывода, что Qdrant не помогает. 73 вызова embeddings обработали 40 031 входной символ; клиент не сообщил точные токены/стоимость. Все пять случайных физических коллекций удалены и проверены, активный alias не переключался.

Необязательная генерация ответов через OpenRouter добавлена в LongMemEval адаптер: она сохраняет JSONL гипотез для официального оценщика, ограничивает входной контекст и выходные токены. На тех же пяти вопросах `openai/gpt-4.1-mini` записала 5/5 ответов без API-ошибок; p50 ответа **1136,47 мс**, 2718 входных и 92 выходных токена, сообщённая API стоимость **$0,0012344** для первого прогона. Простой нормализованный exact-match дал **0/5**, но ручной просмотр показывает две семантически верные переформулировки, одну верную суть с лишней неподтверждённой датой, один ошибочный подсчёт и один отказ из-за отсутствующих после очереди качества фактов. Это не официальный judge score и выборка слишком мала для оценки доли правильных ответов.

Для [LoCoMo](https://github.com/snap-research/locomo) добавлен отдельный адаптер и запущен полный исходный набор из commit [`3eb6f2c`](https://github.com/snap-research/locomo/tree/3eb6f2c585f5e1699204e3c3bdf7adc5c28cb376): 10 диалогов, 1 986 вопросов, 1 982 оценённых по evidence. При прямом FTS-индексировании 5 871 реплики Recall@5 хотя бы одного размеченного evidence = **0,4450**, всех evidence = **0,3865**, MRR = **0,3227**, p50 поиска **83,4 мс**; общий raw-dialogue Recall@5 по оценщику = **0,4115**. Одиннадцать реплик короче ограничения БД были пропущены; два некорректных и три неразрешённых указателя evidence отражены отдельно. Прогон занял **169 с**. Он не использует автоматическое извлечение claims, Qdrant или генерацию ответов; сравнивать его число непосредственно с LongMemEval или опубликованными процентами других систем нельзя.

Для [LongMemEval-V2](https://github.com/xiaowu0162/LongMemEval-V2) добавлен отдельный [потоковый адаптер](benchmarks/longmemeval_v2_adapter.py) и [разбор методики](benchmarks/LONGMEMEVAL_V2.md). Официальный набор содержит 451 вопрос и мультимодальные траектории web/enterprise; публичные вопросы не имеют gold ID подтверждающего state, поэтому локальный FTS-hit нельзя называть recall или accuracy. Проверены SHA256 официальных questions и small haystack. Диагностический [частичный прогон](benchmarks/longmemeval_v2_partial_results.json) на 24 MiB потока trajectories охватил **4/100** траекторий одного enterprise haystack, 201 state, 2 074 текстовых выдержки и 20 вопросов: p50/p95 поиска **677,85/717,19 мс**, индексация **5 983,67 мс**. У 18/20 вопросов все top‑5 выдержек пришли из одной траектории; 752 456 символов accessibility tree были усечены, 201 ссылка на screenshot не индексировалась. Это демонстрирует недостатки текстового маршрута на V2, но охват лишь 4% haystack и отсутствие изображений не позволяют вывести официальный QA/LAFS. Полный 1,2-ГБ файл траекторий, мультимодальные данные (~7 ГБ), reader и judge не загружались и не запускались; адаптер допускает полный офлайн-прогон при предоставлении корпуса. Пять новых тестов формата и изоляции прошли.
Повторная проверка полного V2-корпуса подтвердила официальный размер текстовых trajectories **1 195 604 539 байт**, зафиксированную ревизию и SHA-256 `363cec9a8e87aa8d9101ce4e600aadbf7031d674056ebe4f969e8424abc5f3c6` из manifest. Свободного места на C: было около 14,86 ГБ, но измеренная скорость Range-загрузки составила 0,2–0,5 МБ/с (ориентир 40–100 минут); `hf_xet` за минуту не начал передачу. Оба процесса остановлены без изменения рабочей базы/Qdrant. Даже полная текстовая загрузка не даст официальную QA/LAFS без ~7 ГБ screenshot assets и reader/judge; ограничение замера сохранено явно.

Анализ соответствия методик: LongMemEval adapter отправлял **целые реплики** напрямую в `_add_claim`; это не обычный `sync_turn` Hermes. Полный сухой прогон `benchmarks/longmemeval_ingestion_probe.py` без записи сравнил прямое добавление с `_ingest_text` и эвристикой `on_session_end`. Прямое добавление приняло 794 из 896 размеченных реплик и поставило 102 в очередь. Производственное извлечение плюс эвристика конца сессии приняло кандидат только у **6 из 842** размеченных пользовательских ходов и у **0 из 54** ходов ассистента; 774 пользовательских и 53 ассистентских не дали кандидата. Поэтому 102 поставленных в очередь хода в прямом адаптере не отражают продакшн-очередь. Основная причина — триггерное извлечение фактов и штраф ответам ассистента, а не только порог качества. Смягчать порог целых длинных реплик опасно: в том же прямом сценарии проходили тысячи неразмеченных ответов ассистента. Для поиска истории диалога внедрён отдельный, выключенный по умолчанию эпизодический путь с проверенным происхождением и изоляцией владельца; он не делает сырую переписку доверенными фактами.

Предварительный парный опыт на 30 стратифицированных официальных вопросах LongMemEval измерил отдельные эпизодические выдержки при одинаковом FTS и бюджете из пяти результатов. Продакшн-подобный `_ingest_text` не нашёл размеченное evidence ни для одного из 30 вопросов; добавление двух scoped эпизодических выдержек дало recall-any **0,70**, recall-all **0,3667**. Из 57 размеченных ответных ходов 56 сохранились как эпизоды, ни один не стал доступным claim. p50/p95 поиска эпизодов — **2,74/4,14 мс**, общий размер выданного текста — 16 067 символов. Это маленькая заранее выбранная выборка и локальный нестрогий guard; она не измеряет качество ответа, безопасность действующего шлюза или прирост на полном корпусе. Для рабочего профиля функция остаётся выключенной до явного opt-in.

Полный повторный [прогон production `sync_turn`](benchmarks/full_oracle_episode_results.json) на 500 официальных LongMemEval oracle-вопросах после исправления ложного совпадения `DAN` в именах и словах захватил **896/896** размеченных и **10 936/10 960** всех реплик. 24 строки были отклонены (16 секретным фильтром и 8 локальным write guard); среди размеченных нет отклонённых строк, ошибок ingest и read guard drops тоже нет. На 479 вопросах с размеченным evidence при одинаковом бюджете 3 claims + 2 episodes против 5 claims evidence-any составил **66,18% против 0,84%**, evidence-all **34,45% против 0%**, recall размеченных реплик **41,07% против 0,45%**. p50/p95 инструмента эпизодов — **2,87/4,73 мс**; выдано 996 выдержек общей длиной 289 813 символов. Отличие 479 оцениваемых вопросов от 470 в raw-turn oracle замере связано с другой проверкой разрешимости ссылок на evidence в production adapter; метрики двух адаптеров напрямую не смешиваются. Это полный retrieval-прогон в изолированных профилях с локальным нестрогим guard, без генерации ответов, Qdrant и проверки в живом чате. Подписанный `hermes_trust_core` в среде замера недоступен; автоматический prefetch остаётся отдельным opt-in и по умолчанию выключен.

На ограниченной выборке первого диалога LoCoMo production capture сохранил **82/82** размеченных реплик. Среди 48 вопросов с evidence пять автоматически извлечённых claims дали evidence-any/all **0/0**; три claims плюс два эпизода дали **29,17% / 27,08%** и recall размеченных реплик **17,07%**. p50/p95 поиска эпизодов — **1,72/2,35 мс**. Это один диалог из десяти и не оценка ответов; [методика и результаты](EPISODIC-FALLBACK-DESIGN.md) приведены отдельно.

Отдельный локальный замер рабочего эпизодического запроса на 5 000 синтетических строках одного чата дал p50 **17,12 мс**, p95 **18,05 мс** для 30 последовательных FTS+guard запросов с двумя выдержками. Он не включает параллельную нагрузку. Эпизоды после последней контрольной точки восстановления намеренно не реплицируются в JSONL и могут быть потеряны при восстановлении; FTS восстанавливается из строк контрольной точки. Истёкшие строки перестают выдаваться сразу и физически удаляются при следующем захвате. Автоматическая вставка в prompt реализована с отдельным host opt-in, но в рабочем профиле остаётся выключенной до оценки подписанного строгого guard и качества ответов.

Независимый review пакетной транзакции обнаружил и воспроизвёл дополнительные дефекты: неизвестный `mode` запускал однократную запись, пакет мог обновить claim при отсутствующем FTS-триггере и ID пакета повторялся при вызовах в одну секунду. Исправлены проверка режима, отказ до записи при неполном наборе индексных триггеров и случайный UUID. Также обнаружено продвижение приватного evidence в глобальный claim через `merge_claims` и сохранение секретоподобного текста в заметке merge; оба пути (`merge_claims` и атомарный пакет) теперь требуют одинаковой области читателей и очищают заметку/резолюцию. Для `chat` и `private` проверка видимости дополнительно требует совпадения bot ID, поэтому одинаковый session ID у двух ботов не объединяет их память. Целевые регрессии покрывают эти сценарии.

Вторая проверка нашла такие же пересечения областей в компиляции темы, vacuum, противоречиях и импорте, а также захват владельца при совпадении текста у двух ботов с одинаковым session ID. Производные записи теперь сохраняют исходную область читателей или отказывают при смешивании; точный хеш, SimHash и ключи графа учитывают bot ID для `chat`/`private`. Причины и решения противоречий очищаются до сохранения. Операторская миграция старых строк `chat`/`private` требует явного bot ID вместе с session ID; отсутствующие сведения не угадываются. Эти пути проверены изолированными воспроизведениями и регрессиями.

Третий security sweep нашёл перенос частного содержания через `_curate`, федеративное слияние, исправление пользователя и оба маршрута импорта. Дубликаты в curation теперь сопоставляются только внутри одной области видимости. Федерация не меняет запись другого бота при совпадении хеша, сразу создаёт новые claims с владельцем `chat` и откатывает отдельную строку, если журнал изменений не записался. Без явного `target_claim_id` исправление не меняет найденную по сходству общую/проектную запись и сохраняет новый текст в текущем чате; исправление private claim с явной целью остаётся private. Обычный и bundle импорт привязывают новые claims к текущему чату или его private scope; совпавший ID общей записи не даёт импорту переписать её. Обычный импорт принимает evidence и contradictions только для claims, перечисленных в том же payload, чтобы не дописать частный текст к существующему общему claim; он также синхронизирует `normalized_claim` и хеш при обновлении. Bundle отдельно сообщает записи, поставленные в review queue. Также убрана запись сырого caller query в события вызова global claim и evidence от `mark_used`; при запуске старые `recall_events.query` и `recall_feedback.query` очищаются. `_why_believe` принудительно возвращает пустой query даже до миграции. Изолированные тесты воспроизводят перечисленные границы и успешный откат федеративной строки.

Отдельный [формальный security scan](SECURITY-SCAN-2026-09-20.md) исходного снимка рабочей копии подтвердил ещё две проблемы (статический анализ, частичное покрытие). Модельный `add_preference_rule` принимал самозаявленный `source=explicit` и `global`, после чего правило попадало в системный блок. Теперь этот инструмент сохраняет только ожидающего проверки кандидата в текущем чате; правило не создаёт curated claim и не выдаётся preference layer. Локальный [операторский инструмент](tools/attest_preference.py) показывает точное правило и при `--apply` требует хеш, выданный предварительным просмотром. Он делает резервную копию и атомарно записывает отдельное подтверждение с хешем текста, приоритета и владельца; изменённый кандидат не пройдёт проверку. Модель не может обновить существующего кандидата или подтверждённое правило. Только неизменённое подтверждённое правило или каноническая встроенная политика попадает в системный блок. Старые метки `user`/`explicit` и даже возможная старая метка `host_attested:user` без отдельной записи не дают доверия. Второе замечание касалось сырых элементов `post_task.changed_files/backups/services`, `decision.alternatives` и `source` обеих операций: теперь эти поля и исходный `topic` проверяются на секреты до записи в обычные таблицы SQLite; длина списков ограничена. Вспомогательная строка и соответствующий claim записываются в одной транзакции; ошибка записи claim откатывает первую строку. Подставленный моделью `source` не может придать записи curated provenance: claims этих инструментов помечаются как неподтверждённые и ограничены текущим чатом. Скалярные поля и `mistakes` по исходному пути уже проходили redaction. Гипотеза обхода document scope при нормальном `initialize()` не подтвердилась и в список дефектов не включена.

Последующая прицельная проверка обнаружила тот же обход provenance в общих `add_claim` и `write_firewall(mode=apply)`: модель могла передать `source=decision` и `visibility_scope=global`, получая `verified` для своего текста. Обе публичные операции теперь принудительно используют недоверенный источник и область текущего чата; старые journal replay-вызовы сохраняют историческую семантику только через внутренний неподлежающий подделке канал. Модельные `add_mistake` и `add_task_capsule` тоже больше не создают автоматически проверенные глобальные claims. `add_project_profile` сохраняет профиль только для активного проекта, не принимает модельное `verified/last_verified_at`, а его claim остаётся неподтверждённым. Утверждение старого review item теперь сохраняет новый claim только в текущем чате без автоматической проверки; bundle import тоже использует недоверенный источник. Обычный импорт при изменении существующего claim отзывает старый `verified` и ставит источник `model_tool:import`. Однократная миграция снимает неподтверждённую метку `verified` у исторических claims с curated source и обнуляет старую модельную отметку проверки профиля; текст и область видимости этих записей не меняются. Перед миграцией рабочая база содержала четыре таких `post_task` claims: один chat и три project; исходное происхождение по одной строке `source` восстановить нельзя.
Финальный provenance sweep закрыл операции, которые могли менять уже видимый общий или `verified` claim через `update_claim`, `rewrite_claim`, evidence, pin, merge, transaction, bulk compile/curate/vacuum/normalize/immune, decay/GC и undo. Модель может менять только свои `chat/private` claims; её правки и совпадение по хешу снимают недоказанную проверку, а evidence получает модельный source. Исправление, вызванное инструментом модели, теперь хранится как неподтверждённый кандидат и не попадает в preference layer под видом наблюдённого пользовательского текста: claim-items этого слоя допускают только host-observed `turn:user:*`, а правила по-прежнему требуют отдельной attestation. Подписанный scoped backup и restore ограничены `chat/private` claims, поэтому общая запись с тем же origin session не попадает в архив. Новые проверки находятся в `tests/test_model_mutation_provenance.py`; их нельзя считать доказательством отсутствия иных дефектов вне исследованных путей.

### Парное сравнение ранжирования

Изолированный [A/B-скрипт](benchmarks/retrieval_diversity_ab.py) сравнил одинаковые индексированные данные и кандидаты на полном LongMemEval oracle (500 вопросов, 470 с evidence) и LoCoMo (10 диалогов, 1986 вопросов, 1982 с evidence); [полные метрики](benchmarks/retrieval_diversity_ab_results.json). Пересортировка уже существующего штрафа за повтор источника подняла LongMemEval session recall-all@5 с **0,7915 до 0,8000** (7 улучшений, 3 регресса), но не изменила LoCoMo. Текстовый MMR поднял LongMemEval до **0,8021** (8 улучшений, 3 регресса), прежде всего multi-session **0,5785 → 0,6198**, но снизил knowledge-update **0,8750 → 0,8611**. На LoCoMo тот же MMR снизил evidence recall@5 **0,4115 → 0,3799**, recall-all@5 **0,3865 → 0,3577**, с потерями во всех пяти категориях (18 улучшений, 75 регрессов по вопросам). Медианная задержка поиска осталась около 18 мс на LongMemEval и 87 мс на LoCoMo.

Отдельный [ограниченный пилот](benchmarks/retrieval_event_pilot_results.json) охватил 120 стратифицированных LongMemEval вопросов и 250 LoCoMo вопросов из первых пяти диалогов. Осторожное разнообразие по времени события подняло LongMemEval session recall-all@5 **0,8417 → 0,8583** (2 улучшения, 0 регрессов), но снизило LoCoMo evidence recall@5 **0,3232 → 0,3192** (0 улучшений, 1 регресс в категории 2). **Продакшн-ранжирование не менялось:** ни один вариант не показал прирост на обоих наборах без потерь.

[Парный замер FTS и OpenRouter+Qdrant](benchmarks/PAIRED-HYBRID-FTS-2026-09-20.md) использовал 30 стратифицированных официальных LongMemEval вопросов, два изолированных профиля на каждый случай и одинаковую запись. В 27 случаях с evidence полный возврат нужных сессий @5 составил **0,7037 FTS против 0,7407 hybrid** (один выигрыш, ноль проигрышей), но возврат всех нужных ходов остался **0,3704** в обоих режимах. Медиана/p95 поиска составили **20,66/47,21 мс FTS против 1953,6/8548,41 мс hybrid**. Паритет записи 30/30, ошибок нет; 429 записей принято и 250 поставлено в очередь в каждом режиме. Гибрид сделал 424 embedding-операции по 208 468 входным символам; точные токены и стоимость клиент не выдал. Временные коллекции удалены, активный alias не менялся. Малый прирост на такой выборке не оправдывает переключение производственного ранжирования по умолчанию; Qdrant/OpenRouter остаются доступными в настроенном гибридном режиме.
