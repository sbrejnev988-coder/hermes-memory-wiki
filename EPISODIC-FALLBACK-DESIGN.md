# Scoped episodic evidence: benchmark and rollout boundary

Episodes are short, low-trust excerpts of user or assistant dialogue captured only by the Hermes `sync_turn` lifecycle. They are searchable evidence, never verified facts, preferences, graph edges, or instructions. The feature is **off by default**.

## Why a separate capture path is necessary

The direct `_add_claim` LongMemEval adapter accepted 794 of 896 answer-labeled turns, but that adapter feeds whole dialogue turns to claim admission. A separate probe of the production `_ingest_text` extraction path found accepted candidates in only **6 of 842 gold user turns and 0 of 54 gold assistant turns**, even with a session-end heuristic. The existing owner-aware `review_queue` therefore cannot recover most missed dialogue: most source turns create no candidate at all. Host session JSON files are also unsuitable as a general index: they may contain system/tool messages and lack reliable bot ownership.

The [paired pilot](benchmarks/episodic_fallback_probe.py) uses the pinned official LongMemEval oracle JSON with temporary per-question profiles, no Qdrant, and the actual `_ingest_text` path. In the first five answer-labeled questions per type (30 questions; 57 gold turns), top-five claim retrieval found no gold answer turn. A two-excerpt, exact bot/chat episode supplement retrieved at least one gold turn for 70% of questions and every gold turn for 36.67%. The fixed five-slot variant (three claims plus two episodes) had the same scores. It archived 56/57 gold turns, used 16,067 excerpt characters across questions, and local FTS search took p50 2.74 ms, p95 4.14 ms. These are **retrieval evidence** metrics on a small, biased sample, not answer accuracy or a production security verdict. The isolated pilot used a non-strict local guard and did not run the full Hermes prompt path.

The LoCoMo raw-dialogue FTS baseline recalled all labeled evidence at five in 38.65% of 1,986 questions. Its adapter bypasses extraction, so it measures ranking limits after evidence is present; it cannot validate episode capture or the same two-slot supplement.

A separate production-path LoCoMo sample used the official first conversation and 50 QA (48 evidence-scored). All 82 labeled gold turns were captured by `sync_turn`; five automatically ingested claims gave evidence any/all at five of 0/0, while a fixed budget of three claims plus two episodes gave evidence-any 29.17%, evidence-all 27.08%, and gold-turn recall 17.07%. Episode query p50 was 1.72 ms and p95 2.35 ms. One conversation is too small for a release-wide estimate, and no answers were generated.

The full [production-path LongMemEval probe](benchmarks/full_oracle_episode_probe.py) processed all 500 official oracle questions (SHA-256 `821a2034d219ab45846873dd14c14f12cfe7776e73527a483f9dac095d38620c`) through host `sync_turn` in separate temporary databases/bots. Of 479 questions with answer-turn labels and 896 gold turns, all 896 gold turns entered the episode table. A fixed five-slot comparison gave claim-only evidence-any/all 0.84%/0%, versus 66.18%/34.45% for three claims plus two episodes. Gold-turn recall rose from 0.45% to 41.07%. The episode tool returned 996 excerpts and 289,813 excerpt characters, with p50 2.87 ms and p95 4.73 ms. Write-time screening rejected 16 secret turns and eight guard-unsafe turns from 10,960 total turns; no gold turn, read result, or ingestion call was rejected. The local count-only output is deliberately not versioned until it is paired with a complete provenance manifest.

The first full pass found a guard false positive: an unbounded, case-insensitive three-letter injection marker matched ordinary words such as “Jordan”, “Indonesian”, and “guidance”. All 15 initially missed gold turns were falsely rejected. The guard now requires surrounding attack context for that marker while preserving ordinary names and words. After that fix, capture rose from 881 to 896 gold turns. Evidence-any fell slightly from 67.01% to 66.18% because additional benign rows changed BM25's top-two ranking; capture coverage and retrieval ranking must be evaluated separately.

This comparison fixes five **retrieval slots** and caps episode content at 800 characters, but does not equalize every claim's rendered length or measure generated answers. It uses local FTS, no Qdrant/OpenRouter, and the non-strict local guard because the signed shared trust core was unavailable in the isolated profile. The per-question databases contain no adversarial foreign rows, so ACL safety comes from separate cross-bot/chat regression tests. The LoCoMo sample maps both human speakers into the user channel and cannot validate assistant-role labeling.

## Production boundary

- `MEMORY_WIKI_EPISODIC_ENABLED=1` is a host setting. Default `0` creates no transcript records. Only primary/foreground `sync_turn` captures; tool-supplied `source=turn:user:*`, `_ingest_text`, imports, and document text cannot create episodes.
- Every new row stores an explicit host bot ID, database-bound chat hash, role, configured visibility (`chat` by default), creation time, and expiry. `MEMORY_WIKI_EPISODIC_SCOPE=bot` must be set by the host before capture to permit the same bot's cross-chat retrieval; a later scope change never widens old rows. A model query cannot choose scope or owner.
- Write-time raw-secret scanning rejects the whole turn, then redaction and the injection guard screen the bounded excerpt. Query-time secret scan and guard repeat before output. SQL filters the bot/chat and expiry **before** its 40-row candidate limit. A result includes `trust_level=untrusted` and `source=host_attested_sync_turn`; the query returns at most five excerpts, 350 characters each, 800 characters total. Neither write nor read feeds claim, preference, or graph promotion.
- Default retention is 30 days, with host-configurable 1–365 days; the default per-bot quota is 5,000 rows and 8 MB, capped at 20,000 rows and 32 MB. Expired rows disappear from queries immediately and are physically removed on the next capture by that bot. The host-only `episodic_memory.delete_episodes(provider, scope='all')` erases all of that bot's episodes; `scope='chat'` or `'bot'` narrows the deletion. FTS triggers remove/update indexed terms in the same SQLite transaction.
- Episodes are included in host-level logical journal checkpoints, with FTS derived from rows and rebuildable. They are intentionally **excluded** from model-created scoped snapshots. `sync_turn` is outside the model-tool journal; episodes captured after the latest checkpoint can be lost in a journal rebuild. That bounded loss is preferable to putting raw dialogue into the append-only JSONL journal. Host full backups may contain episodes and require the same access controls as the SQLite database.
- `memory_wiki_query_episodes` is an explicit gated query. An isolated production-query smoke with 5,000 synthetic same-chat rows and 30 sequential searches returned two excerpts at p50 17.12 ms, p95 18.05 ms. A second host opt-in, `MEMORY_WIKI_EPISODIC_PREFETCH=1`, can add at most two excerpts to bounded automatic prefetch only when guard-safe relevant claims fall below the configured minimum and at least 0.5 seconds remain. The separate block is XML escaped, explicitly untrusted, owner-bound in the cache signature, and absent from trusted claim/preference/graph state. Both the smoke and the pilot's p95 4.14 ms exclude concurrent SQLite load, the full prompt builder, and Qdrant/OpenRouter delays. Both feature flags remain off by default.

## Remaining evaluation

Install the signed `hermes_trust_core` into an isolated benchmark profile and rerun the full paired evaluation under strict guard, including adversarial foreign rows and prompt-injection cases. Measure the complete prompt/prefetch path under concurrent use, not only the episode query. Evaluate answers with the official model-judged QA method before any claim of end-to-end improvement or enabling prefetch by default. If the signed core is unavailable, local-guard results cannot establish strict production guard behavior.

Reproduce the full offline retrieval run with `python benchmarks/full_oracle_episode_probe.py --dataset PATH_TO_LONGMEMEVAL_ORACLE_JSON --limit 500`. It uses temporary profiles; do not point it at the live Hermes database. Reproduce the bounded LoCoMo check with `python benchmarks/locomo_episode_probe.py --dataset PATH_TO_LOCOMO10_JSON --conversations 1 --questions-per-conversation 50`.
